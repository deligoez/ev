# ev 0.1.0 — agent-first home inventory

## 1. Decision

`ev` is a command-line home inventory whose primary user is an AI agent working in
conversation with a person standing at the shelves. The person reports what is where; the
agent records it through `ev`; either of them asks `ev` where something is.

0.1.0 ships a Rust workspace with two crates — a `core` library that owns the data model,
the rules and the storage, and a `cli` binary named `ev` — plus a Claude Code skill that
teaches an agent the workflow. A graphical app is deferred (§10) and will reuse `core`.

One database holds any number of homes. A car, an office or a storage unit is recorded as a
home of its own.

## 2. Why

The inventory started as hand-written Markdown files maintained by an agent. That record
drifts: the same container carried two codes in two files, a planned move and a completed
move looked alike, and "where is the Flipper Zero?" could only be answered by grepping
prose. General-purpose home inventory apps are built for a person tapping a screen, not for
an agent issuing commands and reading structured results. `ev` makes the agent's writes
consistent by construction and its reads machine-parseable.

Rust over Go: the later app layer is expected to be Tauri, and a shared Rust `core` lets
the CLI and the app run the same rules against the same database.

Several homes are supported from the first release because the root of the tree is the one
thing that cannot be changed later without rewriting every record's path.

## 3. Data model

### 3.1 Everything is a node

Homes, rooms, furniture, compartments, drawers, boxes, bags and items are all **nodes** in
one tree. Any node may hold child nodes: a bag becomes a container the moment something is
put in it, and an item can hold other items. `kind` is a label that describes a node; apart
from the placement rules of §3.2 it grants or withholds nothing.

Each node has:

| Field | Required | Meaning |
|---|---|---|
| id | yes | Integer assigned by `ev`, never reused |
| name | yes | Free text, may repeat across nodes |
| kind | yes | One of `home`, `room`, `furniture`, `container`, `item` |
| parent | see §3.2 | The node that holds it |
| code | no | Human label printed on the physical object, e.g. `K4x4-07-Ü`, `S5-01` |
| address | no | Free text, homes only |
| qty | no | Positive integer count for a record that stands for several identical things; absent means one |
| note | no | Free text |
| tags | no | Set of short lowercase strings |
| theme | no | Free text describing what a node is used to hold, e.g. "ses ve kablo" |
| fill | no | Estimated fullness, integer 0–100 |
| photos | no | List of absolute file paths; `ev` stores the path, not the file |
| state | yes | `active`, `candidate`, or `gone` (§3.3) |
| lost | yes | Whether the node's whereabouts are unknown (§3.6); false by default |

### 3.2 Tree invariants

1. A `home` has no parent.
2. A `room`'s parent is a `home` or another `room`.
3. Every other node's parent is any node that is not `gone`. Such a node may have no parent
   only while it is lost (§3.6).
4. A node cannot be moved into itself or into any of its descendants.
5. A `code` is unique among nodes whose state is not `gone`, across every home, and is not
   made only of digits.
6. Moving a node moves its whole subtree.
7. A node whose state is `gone` cannot be a parent or a move target.
8. `ev edit <ref> kind=<k>` may change a node's kind; rules 1–3 are checked against the new
   kind.

A command that would break an invariant changes nothing and exits with code 5 (§6).

```
Ev (home)
└─ Yatak odası (room)
   └─ Giyinme odası (room)      ← a room inside a room: allowed
      └─ Gardırop (furniture)
```

`ev move "Giyinme odası" --to Gardırop` exits 5 (rule 2), and so does
`ev move "Yatak odası" --to "Giyinme odası"` (rule 4).

### 3.3 Lifecycle: candidate, then gone

A node that leaves the home carries a disposition — `trash`, `give` or `sell`. It is usually
set aside first and only later actually leaves, so leaving is two steps; when something is
thrown away on the spot, one command does both.

| From | Command | To | Effect |
|---|---|---|---|
| `active` | `ev dispose <ref> --as <d>` | `candidate` | Stays in the tree where it physically is; carries disposition `d` |
| `candidate` | `ev restore <ref>` | `active` | Disposition cleared |
| `candidate` | `ev gone <ref> [--as <d>]` | `gone` | Leaves the tree; `--as` replaces the disposition |
| `active` | `ev gone <ref> --as <d>` | `gone` | Both steps at once; history records dispose then gone |
| `active` | `ev gone <ref>` | — | Refused, exit 5: how it left is unknown |

A `gone` node is no longer a candidate: `ev disposals` does not list it. It keeps its last
disposition, so the record answers "did we sell that or give it away?".

`dispose` and `gone` refuse, with exit 5, a node that still has non-`gone` children, and
list those children in the error payload.

### 3.4 Pending moves

A move can be **planned** and later **confirmed**, because the agent proposes a destination
and the person carries the item.

- `ev move <ref> --to <ref> --plan` records a pending move. The node stays where it is and
  shows the pending destination.
- `ev pending` lists every pending move.
- `ev done <ref>` applies the node's pending move; the invariants of §3.2 are checked at
  that moment, not at planning time.
- `ev cancel <ref>` drops the node's pending move.
- A node has at most one pending move; planning a second one exits 5.
- `ev move <ref> --to <ref>` without `--plan` moves immediately and drops any pending move
  the node had.

### 3.5 History

Every change is appended to an event log that is never edited or pruned: create, edit,
move, plan, done, cancel, dispose, restore, gone, lost. `ev history <ref>` returns a node's
events in order, each with its timestamp and the before/after values it changed.

### 3.6 Lost

A node whose whereabouts are unknown is **lost**.

- `ev lost <ref>` marks a node lost. It keeps its parent as its **last seen** place, so the
  search can start there.
- `ev add <name> --kind <k> --lost` without `--in` records something known to exist whose
  place was never known; it has no parent.
- `ev lost` with no reference lists every lost node with its last seen path, or none.
- Any move of a lost node clears the flag; a planned move does not, `ev done` does.
- A lost node's descendants are not flagged themselves; their path runs through a lost node.

## 4. References

Every command argument that names a node is a **reference**, resolved in this order:

1. A reference made only of digits is an id.
2. Otherwise it is compared, after folding (§5), against codes; an exact match wins.
3. Otherwise it is compared, after folding, against names; an exact match wins.

No match exits 3. More than one match at the deciding step exits 4, and the payload lists
every candidate with its id, code, name and path, so the agent can retry with an id. A
partial name never resolves; the agent searches with `ev find` and retries with the id.
`gone` nodes are excluded unless the command is `history` or the flag `--include-gone` is
given.

| id | code | name | place |
|---|---|---|---|
| 42 | `S5-01` | Ses ve kablo | Ev › Kiler |
| 57 | `K4x4-07-Ü` | Çekmece | Ev › Salon › K4x4 |
| 88 | — | Flipper Zero | Ev › Salon › K4x4 › K4x4-15-A |
| 91 | — | Anten | Ev › Salon › K4x4 › K4x4-02-Ü |
| 92 | — | Anten | Ev › Salon › Masa |

With that database:

| Reference | Result |
|---|---|
| `42` | node 42 |
| `s5-01` | node 42 |
| `k4x4-07-u` | node 57 |
| `flipper zero` | node 88 |
| `flipper` | exit 3 |
| `anten` | exit 4, candidates 91 and 92 |

## 5. Search and folding

`ev find <text>` returns every non-`gone` node whose name, code, note, theme or tags contain
the text after folding, each with its full path from the home down
(`Ev › Salon › K4x4 › K4x4-15-A › Flipper Zero`) and its lost flag. `--tag`, `--kind` and
`--include-gone` narrow or widen the set.

Folding lowercases with Turkish casing rules, maps dotless `ı` to `i`, and removes diacritics:

| Input | Folded |
|---|---|
| `Çekmece` | `cekmece` |
| `IŞIK` | `isik` |
| `İğne` | `igne` |
| `Kör` | `kor` |
| `Şarj` | `sarj` |
| `Üst` | `ust` |
| `Hâlâ` | `hala` |

So `ev find cekmece` finds a node named "Çekmece", and `ev find ISIK` finds "ışık".

## 6. Command-line contract

Output goes to stdout as JSON when stdout is not a terminal and as readable text when it is;
`--json` forces JSON. Errors, warnings and hints go to stderr only. Exit codes are fixed:

| Exit | Meaning |
|---|---|
| 0 | Success |
| 1 | Internal error |
| 2 | Usage error |
| 3 | Reference not found |
| 4 | Reference ambiguous |
| 5 | Invariant or lifecycle rule refused the change |
| 6 | Database was written by a newer `ev` |

Commands in 0.1.0:

| Command | Purpose |
|---|---|
| `ev add <name> --kind <k> [--in <ref>] [--lost] [field flags]` | Create a node |
| `ev add --batch <file.ndjson>` / `--stdin` | Create many nodes in one call; all or none |
| `ev show <ref>` | One node with its path, direct children, pending move, disposition and lost flag |
| `ev tree [<ref>] [--depth <n>]` | The subtree under a node, or every home |
| `ev find <text>` | Folded search (§5) |
| `ev edit <ref> <field>=<value>…` | Change fields; tags and photos take `+value` / `-value` |
| `ev recode <ref>=<code>…` | New codes for several nodes at once; uniqueness is checked against the final codes, so codes can be swapped or rotated (§19) |
| `ev move <ref> --to <ref> [--plan]` | Move now, or plan a move (§3.4) |
| `ev pending` / `ev done <ref>` / `ev cancel <ref>` | Pending moves (§3.4) |
| `ev dispose <ref> --as <d>` / `ev restore <ref>` / `ev gone <ref> [--as <d>]` | Lifecycle (§3.3) |
| `ev disposals [--as <d>]` | Every candidate, grouped by disposition |
| `ev lost [<ref>]` / `ev found <ref>` | Mark a node lost, list lost nodes, or clear the flag in place (§3.6, §11) |
| `ev history <ref>` | A node's events (§3.5) |

Batch creation lets a line refer to a node created by an earlier line of the same batch, so
a whole box and its contents can be entered in one call.

## 7. Storage

The database is one SQLite file at `~/.ev/ev.db`, created on first use; `--db <path>` or the
`EV_DB` environment variable selects another file. The file records the schema version that
wrote it; `ev` migrates an older file forward and refuses a newer one with exit 6.

The inventory is personal data and never lives in the `ev` repository.

## 8. The skill

`skills/ev/SKILL.md` tells an agent:

- the conversation workflow — the person reports, the agent records, a move is planned,
  the person carries it, the agent confirms with `ev done`;
- that codes are what is printed on the physical labels and must be used as given;
- that uncertainty is recorded as a note, never guessed into a field;
- how to read exit codes 3 and 4 and retry with an id.

## 10. Non-goals for 0.1.0

- A graphical or mobile app (Tauri is the expected route, later).
- Homebrew distribution.
- Copying or storing image files; only paths are kept.
- Sync between machines or multiple users.
- Usage-frequency tracking.
- Importing the existing Markdown records; the agent enters them through the CLI.

## 11. Decisions taken after review round 1

Review round 1 (`spec/.tp-review/0.1.0/review-round-1.ndjson`) found gaps rather than
contradictions. The operator chose to stop reviewing and implement; these decisions close
the gaps and take precedence over any earlier sentence they refine.

1. **Errors.** An error prints nothing on stdout. On stderr it prints one JSON object
   `{"error": {"code", "kind", "message", ...}}` in JSON mode, or a readable message
   otherwise. Exit 4 adds `candidates`; exit 5 adds `details` (for example the blocking
   children).
2. **Output shapes.** Every node in any payload carries `id`, `code`, `name`, `kind`,
   `state`, `lost`, `path` (a list of `{id, code, name}` from the home down) and
   `path_text`. A path segment shows the node's code when it has one, its name otherwise.
   The full shapes are documented in `REFERENCE.md`, not here.
3. **Codes compare folded.** Uniqueness uses the folded code, so `K4x4-07-Ü` and
   `K4x4-07-U` cannot both be active.
4. **Reused codes.** When `--include-gone` is in effect and a code matches several nodes,
   the single non-`gone` match wins; otherwise the reference is ambiguous.
5. **Batch lines.** Each line is a JSON object with the same fields as `ev add`'s flags
   (`name`, `kind`, `in`, `lost`, `code`, `address`, `qty`, `note`, `theme`, `fill`, `tags`,
   `photos`) plus an optional `key`. An `in` of the form `@key` names the node created by an
   earlier line carrying that key.
6. **Exit 2 vs 5.** Malformed input — a missing or unknown field, a value out of range
   (`fill` outside 0–100, `qty` below 1, an unknown kind or disposition) — exits 2. A
   well-formed request the model refuses exits 5.
7. **Transitions outside the §3.3 table** (dispose of a candidate, restore of an active
   node) exit 5. `gone` is final.
8. **A gone node keeps its parent** as the place it left from; rule 3 applies at the moment
   a node is placed, and gone nodes are ignored by the children checks.
9. **Pending moves.** `gone` drops the node's pending move. A refused `ev done` keeps it.
10. **Lost.** Any node except a home may be parentless while lost. `ev found <ref>` clears
    the flag in place and records a `found` event. `--lost` together with `--in` records a
    last seen place.
11. **Tree and show** include candidates and exclude gone nodes; `--depth` is unlimited by
    default.
12. **Folding** trims surrounding whitespace and removes every combining mark, not only
    Turkish ones. An empty search text exits 2.
13. **Database selection.** `--db` wins over `EV_DB`. Writers wait up to five seconds for a
    concurrent writer before failing.
14. **Kept as designed:** `dispose`/`gone` still refuse a node with children (the operator
    prefers explicit handling), and `gone` cannot be undone.

## 12. Changes found in use (0.1.1)

1. **Bundles.** `dispose` and `gone` refuse only when an **active** node is inside. Candidates
   inside are already set aside and do not block, so a set (a dock with its adapter and
   cables inside it) is disposed part by part and then as a whole. When a node goes, every
   candidate inside goes with it, keeping its own disposition, and its `gone` event names
   the node it left with. This refines §3.3 and §11.14.

## 13. Places, ownership and lending (0.3.0)

1. **A place** is anywhere outside the tree that things go to or come from: a person, a household,
   an office. It has one name and any number of aliases (`Mahmutlar`, `Saliha'lar`, `Güneşler`
   name one household). Names and aliases compare folded (§5) with apostrophes ignored, and an
   alias names exactly one place. A place is created the first time a free-text name is used;
   `ev place merge` folds two places into one when they turn out to be the same.
2. **Three optional fields point at a place.** `to`: the node should be taken there. `owner`: the
   node is not ours; it belongs there. `with`: the node is ours and is lent out there — it stays in
   the tree at the place it returns to, like a lost node keeps its last seen place.
3. **`ev for <place>`** lists, for that place, what to take (`to`), what to return (`owner`) and
   what to collect (`with`), each with its current path. With no argument it lists every place that
   has any. The agent runs it whenever the person says they are going somewhere or meeting someone;
   the agent strips Turkish case suffixes (`Mahmutlara` → `Mahmutlar`) before asking.
4. **Lending.** `ev lend <ref> --to <place>` sets `with`; `ev back <ref>` clears it. A node with an
   `owner` cannot be lent.
5. **Returning** something that is not ours is a way of leaving: disposition `return`, so
   `ev gone <ref> --as return` records that it went back.
6. Schema version 2 adds the places and the three fields; a version-1 file is migrated on open.

## 14. Placement: suggest, rules and audit (0.3.0)

1. **The guarantee is completeness, not ranking.** "Where should this go?" is answered by the
   agent from `ev suggest`, which lists every node that can hold something — every room,
   furniture, container, and item that already holds something — each with its path, theme,
   fill, item total and a sample of its contents. Nothing is ranked away and no filter drops a
   holder; `complete.containers` states how many were listed. The agent does the semantic
   matching over that list.
2. `ev suggest` also lists where alike things already are (items whose words or tags match,
   grouped by the holder they sit in) and every placement rule.
3. **Rules are data.** `ev rule add|list|remove` keeps the person's placement rules ("drawers are
   for daily things, rarely used things go to the pantry") in the database, so every session and
   every agent weighs the same rules. A correction ("that other place was better") becomes a rule
   or a theme, never only agent memory.
4. **`ev audit`** reports where the inventory could be tidier: alike things split across several
   holders, holders with items but no theme, and items lying directly in a room or on furniture.
5. **No vector search.** Completeness comes from listing every holder, and a home has hundreds of
   holders, not millions; embeddings would add a model dependency and still only rank. Revisit if
   the holder list stops fitting an agent's context or word mismatches are seen to hide a holder.
6. Schema version 3 adds the rules table.

## 15. Found in use, 2026-09-29

1. **Contents unknown.** A holder whose contents were never inventoried carries `unknown`, so an
   item count of zero is not taken for free space. `ev audit` lists them.
2. **Correcting a mistaken `gone`.** §11.14 said `gone` cannot be undone; it can now, but only as a
   correction with a stated reason (`ev restore --correction`), recorded in the history. It is
   refused while the node's parent is itself gone, and when its code is now used elsewhere.
3. **Word matching in `suggest`.** A query word matches an item word when they are equal, or one
   starts with the other and the shorter has at least four letters.

## 16. Photos (2026-09-29)

1. **ev keeps its own copies.** `ev photo add` copies the file into a `photos/` directory next to
   the database, named by content hash, so a photo outlives the Downloads folder or chat upload it
   came from. §10's "only paths are kept" no longer holds. `ev photo adopt` copies photos that
   older records still reference by an outside path.
2. **Crops.** `--crop x,y,w,h` (fractions 0–1 of the upright photo; EXIF orientation is applied
   first) attaches only the cut-out and records the stored original and the crop, so one drawer
   photo can illustrate every box in it. The agent views each crop after cutting it and redoes
   any that missed.
3. A node holds any number of photos, numbered from 1 (`ev photo list`, `ev photo remove <n>`).
4. **`ev ui` shows the selected node's photo** in its details pane, using the terminal's graphics
   protocol (Kitty in Ghostty) or half-block characters as a fallback; `[` `]` step through a
   node's photos and `o` opens the current one in the system viewer.
5. Schema version 5 adds `source`, `crop`, `note` and `added_at` to photos.

## 17. The tidy-up plan (2026-09-28)

The project started from messy drawers and boxes; recording them is not the goal, putting
them in order is. Until now the order of work lived in the agent's memory and the person had
to say "next is 08-Ü". Decision: the plan is data in ev, the judgement stays with the agent
and the person.

- **Units.** The places a person opens one at a time: the innermost labelled holders, plus
  unlabelled holders standing on their own in a room or on furniture. A holder is a unit when
  none of its children carries a code; everything below a unit is gone through with it. Why:
  codes are physical labels, so they already mark what a person opens.
- **Review.** A unit is `raw` (known only from the first photos), `toured` (every thing in it
  looked at and the person said it is done) or `kept` (the person wants it left as it is).
  A review on a holder covers everything below it. `ev progress` counts them and flags toured
  units whose contents changed since.
- **Observations.** Dated notes on a place — what the agent saw in a photo or heard — kept on
  the place, not in the agent's memory.
- **Tasks.** An ordered list; every task has a reason (`why`) and the places it is about.
  One task is in progress at a time. A task closes only when the person says so, like a move.
- **`ev next`.** The current task with each of its places as `show` gives them, what is
  planned to arrive there, the rules, progress, and — under `organize` — the raw units no
  task covers, so gaps in the plan show.
- **Goal.** `organize` or `track`. A household that does not want a tidy-up still gets
  correct records: under `track` ev offers no gaps and the agent proposes no tidy-up tasks;
  `kept` lets a person say "leave this one alone" place by place even under `organize`.

Schema version 6 (`reviews`, `observations`, `tasks`, `task_nodes`, `settings`).

## 18. Everything waiting, in one list (2026-09-28)

Most of what is "to do" in a home was already state on a node — a planned move, a thing meant
for another household, a disposal, a lost thing, a holder never inventoried. Decision: those
are **not** copied into tasks. A copy would drift from the node (a thing returned with
`ev gone --as return` would leave its task open), which is the class of bug `ev for` had when
one intention sat in two fields. `ev todo` reads them where they live; each leaves the list
by its own verb (`done`, `gone`, `back`, `found`, …).

Kinds that had no state get one, as a mark on the node (one per node and kind):

- **label** — `needed` whenever a code is set or changed, `printed` once the person says so.
  Existing codes carry no mark: nobody knows yet whether their labels exist.
- **broken** — with what is wrong; cleared by `ev fixed`.
- **expires** — a use-by date, `YYYY-MM` meaning the month's last day; due within 60 days or
  past shows in `todo`.
- **sale** — `listed` or `reserved`, with price and where; only on a sell candidate. Selling
  is still `ev gone`.

Needs (things to buy or make) are not in the tree yet, so they are a list of their own,
optionally for a place. `todo` also lists holders whose names are still a guess
("belirsiz", "muhtemelen", "?") — names only, since notes keep history.

In `ev ui` the plan tab becomes Yapılacak: one collapsible section per kind with its count,
empty sections hidden, every line pointing at its node so the details pane shows it.

Schema version 7 (`marks`, `needs`).

## 19. Found in use, 2026-09-29 (evening)

Two things came up while laying out a gridfinity drawer cell by cell, where a box's code is the
cell it sits in (`K4x4-07-A-D2`).

1. **A crop attached to a place is a picture of that place.** The photo-needed list counted only
   whole photos, so a box whose picture was cut out of a drawer photo stayed on the list however
   current the crop was. The crop is attached to the place itself, and a crop of one thing inside
   goes on that thing, so a crop on the place can only picture the place. It now counts.
2. **Codes move with boxes.** When the person moves a tall box back a row and the two boxes there
   forward, three codes rotate. `ev edit` checks uniqueness one node at a time, so a rotation
   needed a throwaway code. `ev recode <ref>=<code>…` sets them together: every reference is
   resolved first, the codes are cleared, and each new code is checked against the nodes outside
   the set. Every changed code gets a `label: needed` mark and an `edit` event, as with
   `ev edit`. All or nothing.

## 20. Languages, settings and a live appearance (2026-09-29)

1. **Two languages, English first.** The words people read — `ev ui` and the readable terminal
   output — are English or Turkish. The English text is the key of every translation, so a
   missing translation shows English rather than a key, and a test fails the build when any
   text passed to `t`/`tf` has no Turkish, or when a translation changes its number of `{}`
   placeholders. JSON and error messages stay English: they are the contract for agents.
2. **The computer's language by default.** `auto` reads the system's preferred language (macOS:
   `defaults read -g AppleLanguages`; elsewhere the locale variables) and uses only its language
   part, so an English system in the Turkish region is English. It reads `defaults` instead of
   calling CoreFoundation because the release is cross-built on Linux, where the macOS SDK is
   not available to link against.
3. **Settings are not inventory.** Language and appearance belong to the person at this
   computer, so they live in `~/.ev/settings.json` (`EV_CONFIG`), not in the database; `ev
   settings` works without a database, and `ev ui` — which still never writes the database —
   writes that file from its Settings tab. A running `ev ui` notices the file change within a
   second, so `ev settings` from another terminal takes effect without a restart.
4. **Follow the terminal, live.** The appearance is `auto`, `dark` or `light`. `auto` turns on
   DEC mode 2031 and asks `CSI ? 996 n` and OSC 11 at start; the terminal's `CSI ? 997 ; 1|2 n`
   reports switch the palette as they arrive. A terminal that never sent such a report is asked
   OSC 11 every three seconds. Dark keeps the terminal's named colours, as `ev ui` always had;
   light uses fixed tones chosen for a white background, since named yellow and cyan are hard to
   read there.
5. **`ev ui` reads its own input.** crossterm 0.29 parses `CSI ? … n` as an unfinished sequence
   and keeps the keys typed after it in its buffer, and reads an OSC reply as Alt-`]` plus text.
   So `ev ui` reads raw bytes on a thread and parses keys, SGR mouse reports, the 997 reports
   and OSC 11 replies itself, handing the rest of the program the same crossterm key and mouse
   events as before. A lone ESC is the Esc key once 30 ms pass without the rest of a sequence.
6. **`ev ui` also asks for the picture protocol itself** (0.8.0). ratatui-image's stdio query
   reads the answer on a thread and, when none comes before its timeout, leaves that thread
   blocked on stdin, where it takes the next key. `ev ui` now sends the same queries (kitty
   graphics, device attributes, cell size, ended by the status report every terminal answers)
   and reads the answers with its own parser; the screen starts on half blocks and switches to
   the protocol when the status report arrives. Inside tmux the query needs passthrough
   wrapping, so there ratatui-image still asks.

## 21. A drawer photo in one step (2026-09-29)

Touring a gridfinity drawer means one overview photo, the whole view on the drawer and a crop
on each box in it — thirteen `ev photo add` calls for one drawer. `ev photo cut <file>
<ref>=x,y,w,h… [--place <ref>]` does it at once. Every reference is resolved and every crop
cut before anything is recorded, and the records go in one transaction, so a mistyped code
leaves nothing half attached. The whole-photo rule of `photo add` applies to `--place`.

## 22. Grids (2026-09-29)

A gridfinity drawer is a grid, and its boxes' codes were already their positions
(`K4x4-07-A-D2`), with the cells each covered written into its note by hand. Decision: the grid
is data.

1. **A holder may have a grid**: columns A…Z from the left, rows 1… from the back (the way the
   person reads a drawer standing in front of it). A box in it covers a rectangle of cells,
   written as two opposite corners or one cell. Two new tables, schema version 8.
2. **Placing is checked against the end state.** `ev cell` takes several boxes at once and
   checks bounds and overlaps after all of them have moved, because the common change is boxes
   trading places, which one at a time would always overlap. All or nothing.
3. **Codes can follow cells.** `--recode` gives each placed box `<holder code>-<back-left
   cell>`, rotating codes the way `ev recode` does, and marks the new labels as needed.
4. **Free cells are where there is no recorded box.** Empty bins that are not records count as
   free. `ev grid` draws the map with each cell showing its box's back-left cell; `ev ui` shows
   the same map in the details of a grid holder, `ev show` carries `cells` and `grid`, and
   `ev suggest` lists each grid holder's free cells.
5. A box moved out of its holder loses its cells; a grid cannot shrink under, or be removed
   from under, placed boxes.
6. The first tab of `ev ui` is called Layout (Yerleşim), not Tree (Ağaç): it shows where
   things are, and a tree is how that is stored.

## 23. Placement that shows its work (2026-09-29)

§14 made the answer complete but left the matching to the agent, and §15.3's word match drowned
in common words ("sensör" is in half the drawer) and missed Turkish forms. The person asked
for a decision that is close to deterministic, says what it weighed — notes included — knows
how much room each box has, and raises new groupings such as moving to a bigger box.
Decision: `ev` ranks, explains the rank, and still lists everything.

1. **A holder is a document.** Its theme, name and note, and the names, tags and notes of the
   things directly inside it, each with a field weight; scored with BM25F and IDF, so a rare
   word (a part code, "LDR") decides more than a common one ("modül"). Every match is reported
   with its word, points and the field or thing it came from. Ties go to the lower id.
2. **Turkish without a model.** Suffix layers are cut and consonants hardened back
   (`kitabı` → `kitap`), but only as far as the inventory's own words allow: the shortest
   shorter form written somewhere on its own wins, a word written on its own is never cut, and
   otherwise the longest stem two words share. Part codes are one word. Snowball's Turkish
   stemmer was tried and cut too deep (`kartı` → `kar`, `lehim` → `leh`).
3. **Knowing when nothing fits.** `coverage` is the share of the query the best holder matched;
   under half, `new_group_likely` says the thing needs a new group rather than the least bad box.
4. **Room is data.** `fill` becomes `room` (yes / little / none / unknown) and goes `stale` when
   the contents changed after the estimate. Boxes get a `size` (`WxDxH` in grid units), schema
   version 9.
5. **Regrouping is a report.** `ev regroup` runs the same score for every thing, leaving the
   thing out of its own holder's words, and reports things better off elsewhere (only on a word
   that says what they are, 1.5× and at least 3 points), mixed boxes, full boxes with the spare
   boxes (`boş kap` + `size`) that are bigger and the grid cells each would fit, nearly empty
   boxes that could merge into a sibling with room, and unknown fills. It changes nothing.
6. **Synonyms are data**, like rules: `ev synonym add "fotosel, ldr, ışık sensörü"` is kept in
   the database (schema 9), so every session searches the same words.
7. **Still no vector search** (§14.5 revisited). Turkish embedding models are 118–512 MB, pull
   in a runtime that breaks the cross-build, are not bit-for-bit deterministic, and rank part
   codes worse than BM25; a home has hundreds of holders. What embeddings would add — knowing
   that an LDR is a light sensor — comes from synonyms and from the agent adding category words
   to the query. Revisit with a small static model (model2vec) fused by rank if word mismatches
   are seen to hide a holder.

## 24. Native release builds (2026-09-29)

Releases were cross-built on one Linux runner with GoReleaser and cargo-zigbuild: four targets
one after another (7 minutes for v0.11.0, and a hung Zig download held it for 7 more), and no
macOS framework could be linked, which is why §20.2 read `defaults` and the TUI asked `date`
for the time zone. Decision: release with dist.

1. **Each target builds on its own kind of machine, in parallel**: both macOS targets on a macOS
   runner, Linux on x86 and ARM Linux runners. Nothing is cross-compiled, so Zig is gone and
   macOS APIs can be linked.
2. **The workarounds go.** The system language comes from `sys-locale` (on macOS the first
   preferred language, as before; §20.2's `defaults` call is superseded), and local times from
   chrono's local time zone.
3. **The rest stays as it was.** The Homebrew formula keeps its name (`deligoez/tap/ev`), the
   hand-written notes in `release-notes/<tag>.md` go on the GitHub release by a small job dist
   calls after announcing, and a pre-release tag tries the pipeline without touching the tap.

## 25. Themes read from contents (2026-09-29)

Placement answers lean on holder themes the way PageIndex's tree search leans on its node
summaries (fikir-atlasi, 2026-09-29): measured against a reviewed answer key, most misses were
holders with no theme or a shared one, not word matching. Decision: `ev themes` gathers the
evidence for a theme; the agent writes it with the person.

1. **Evidence, not a theme.** For each container or furniture with things in it and no theme:
   the words its contents share (stems counted once per thing, rarer first, written as the
   inventory writes them; colours and numbers left out), a sample of the contents, and the
   themed holder those words read most like. Writing the summary is a judgement ev does not
   make; kits recorded as items are named for what they are and are left out.
2. **Shown where the theme is written.** `ev ui` shows the same under a themeless place's
   details; the skill asks for a theme on every toured place.
3. **Measured.** On a copy of the author's inventory, themes from the top three words on the
   four themeless places put three more things in their best place (253 → 256 of 410), and
   hand-written themes did the same while raising the right holder's score on sample queries
   (an antenna cable 29 → 45, a Skådis hook 20 → 36).

## 26. Facets, and a tree that reads as a layout (2026-09-30)

In K4x4-07-A modules and bare parts are kept in separate boxes, and `regroup` proposed moving
the buzzer module into the bare-buzzer box and the RGB LED board into the bare RGB LED box: the
words agree, the kinds do not. A rule in plain words does not reach the ranking. Decision: the
kinds are data.

1. **A facet is a named kind with words.** A holder is in it by carrying its name as a tag (or
   by being inside such a holder). A thing is in it by its own tag, else by a facet word in its
   name (every form it could be cut to counts, so `modülü` names `modül` even where the bare
   word is never written), else by where it is. Schema version 10 adds the facets table.
2. **Another facet is out, not down-ranked.** `suggest` keeps holders of another facet out of
   `similar` and lists them apart (`other_facet`); `regroup` never proposes one. A side
   without a facet is free, so untagged parts of the house behave as before.
3. **Measured.** On a copy of the author's inventory, two facets over 07-A's 21 boxes removed
   both wrong proposals and the "mixed" flag on F3 (35 → 38 of 43 things in their best place;
   253 → 256 in the whole house). The same mechanism is meant for the bookshelves (a genre per
   shelf).
4. **`ev tree` carries each node's theme, fill, size and tags**, so one call reads a drawer as a
   layout; `ev ui`'s fill bars in tree rows, which read `fill` from it, now show.

## 27. Current photos by construction (2026-09-30)

K4x4-07-A was confirmed from several photos of its final state, none of which was attached: the
newest drawer photo still showed an empty D3 that now holds tact buttons, eight of its 21 boxes
showed older photos still, and `ev ui` opened on the oldest photo of each. The rule "attach every
photo" was in the skill; nothing in ev held it.

1. **A grid photo is cut by corners.** `ev photo cut --grid` takes the grid's four corners in
   the photo and cuts a crop for every placed box through a projective map of the plate, so a
   drawer photo refreshes every box at once rather than the ones someone remembered to crop.
   A bilinear split was tried first and drifted toward the front on the real photo: rows further
   back are shorter in a photo.
2. **A tour needs current photos.** `review --status toured` is refused while the place or a
   placed box in its grid has no photo or one older than its last change; `ev photo current`
   is the explicit way to say an old one still holds.
3. **The newest photo is the current one.** Older photos stay as history. `ev ui` opens on the
   newest, with its note in the panel title.
4. **Every node shows its `#id`**, and every command resolves `#<id>`, so the person can point
   at a thing that has no code.
5. **A grid is drawn as its plate**, each box a frame over its cells: a box covering several
   cells reads as one box, and a free cell as bare plate.
